# YC FinOps Auto-Tagging

Serverless-функция Yandex Cloud, которая автоматически проставляет метку
`created_by` на новые ВМ, реагируя на события Audit Trails в реальном
времени. Задача — **атрибуция затрат в FinOps**: понимать, кто создал
ресурс (и, соответственно, на какую команду/центр затрат его отнести),
даже если политика тегирования не была включена на момент создания.

🇬🇧 English version: [README.md](README.md)

## Зачем это нужно

Одна из самых частых FinOps-проблем — нераспределённые расходы: ВМ
существует, стоит денег, а кто её владелец — никто сказать не может. На
зрелой платформе это решается принудительным тегированием через политики
при создании ресурса. Здесь используется другой подход — источником
истины становится собственный аудит-лог облака, поэтому разметку
владения можно добавить *постфактум*, не меняя то, как команды создают
ресурсы.

Подход основан на паттерне из статьи Inferit на Хабре
[«Как автоматизировать FinOps-разметку ресурсов в Yandex Cloud с помощью логов»](https://habr.com/ru/companies/inferit/articles/1057926/)
(которая, в свою очередь, адаптирует референсный пример Yandex Cloud по
реакции на события ИБ через Audit Trails). Этот репозиторий — независимая,
покрытая тестами реализация сценария с реалтайм-триггером из статьи, плюс
пример запроса для пакетного/исторического сценария.

## Два подхода к разметке

| | Реалтайм-триггер (функция в этом репо) | Пакетный/исторический анализ |
|---|---|---|
| **Задержка** | Секунды | От часов до дней (запуск по расписанию) |
| **Требуемая инфраструктура** | Аудит трейл → лог-группа → триггер Cloud Function | Аудит трейл → бакет Object Storage → Yandex Query |
| **Профиль стоимости** | Плата за вызовы функции + хранение лог-группы | Плата за объём данных, прочитанных YQL за запуск |
| **Когда лучше подходит** | Постоянная разметка всего, что создаётся дальше | Разовая "догонка" уже существующего неразмеченного парка |

Оба подхода читают одно и то же событие Audit Trails
(`yandex.cloud.audit.compute.CreateInstance`); пример запроса для
второго подхода — в
[`batch_scenario/historical_vm_creators.sql`](batch_scenario/historical_vm_creators.sql).

## Архитектура (реалтайм-триггер, этот репозиторий)

```
 Создание ВМ  ──▶  Аудит трейл  ──▶  Лог-группа Cloud Logging  ──▶  Триггер Cloud Logging
                                                                          │
                                                                          ▼
                                                              Cloud Function (этот репозиторий)
                                                                          │
                                                    fail-fast фильтр: CreateInstance + DONE?
                                                                          │
                                                                          ▼
                                                     Compute API: Get → объединить labels → Update
                                                                          │
                                                                          ▼
                                                    У ВМ теперь есть label created_by=<очищенное имя>
```

## Структура проекта

```
yc-finops-autotag/
├── index.py                     # Точка входа Cloud Function (handler)
├── audit_event_parser.py         # Разбор конверта LoggingMessageBatch триггера
├── label_sanitizer.py             # Приведение произвольных имён к валидным значениям label
├── vm_labeler.py                   # Вызовы Get/Update Compute API (ленивый импорт gRPC)
├── batch_scenario/
│   └── historical_vm_creators.sql   # Пример YQL для пакетного/исторического подхода
├── tests/
│   ├── test_audit_event_parser.py
│   └── test_label_sanitizer.py
├── requirements.txt
├── requirements-dev.txt
└── .gitignore
```

Как и в проекте [yc-vm-scheduler](../yc-vm-scheduler), логика разбита на
небольшие, независимо тестируемые части — вызовы cloud SDK изолированы
от чистой логики парсинга/валидации:

- **`audit_event_parser.py`** — без зависимости от cloud SDK.
  Разворачивает конверт сообщения триггера, применяет fail-fast фильтр
  (соответствует ли лог целевому `event_type`/`event_status`) и достаёт
  ID инстанса и имя инициатора из записи аудита. Полностью покрыт тестами.
- **`label_sanitizer.py`** — без зависимости от cloud SDK. Реализует
  правила Yandex Cloud для значений label (нижний регистр, ограниченный
  набор символов, лимит 63 символа, обязательно начинается с буквы) как
  одну чистую функцию. Полностью покрыт тестами, включая крайние случаи
  (полностью числовое или полностью невалидное имя).
- **`vm_labeler.py`** — единственный модуль, обращающийся к Compute API:
  читает текущие labels, объединяет с новым, отправляет обновление.
  Импорты gRPC/protobuf ленивые, чтобы модуль оставался лёгким и легко
  мокался в тестах.
- **`index.py`** — оркестрация: проходит по батчу, применяет фильтр,
  вызывает остальные два модуля. Тип целевого события, тип ресурса и
  ключ label настраиваются через переменные окружения, а не зашиты в
  коде — ту же функцию можно перенаправить на другие типы ресурсов
  (диски, базы данных и т.д.) без изменения кода.

## Конфигурация

| Переменная окружения      | По умолчанию                                    | Описание                                                    |
|-----------------------------|---------------------------------------------------|-----------------------------------------------------------------|
| `TARGET_EVENT_TYPE`          | `yandex.cloud.audit.compute.CreateInstance`      | Тип события аудита, на которое реагируем.                     |
| `TARGET_RESOURCE_TYPE`       | `compute.instance`                               | Тип ресурса для поиска в `resource_metadata.path`.            |
| `LABEL_KEY`                  | `created_by`                                     | Ключ label, в который пишется очищенное имя инициатора.        |

## Необходимая настройка в облаке

1. **Аудит трейл**, отфильтрованный по `yandex.cloud.audit.compute.CreateInstance`,
   с выводом в лог-группу Cloud Logging. Ограничьте область действия
   минимально необходимой организацией/облаком/каталогом — и по деньгам,
   и по радиусу возможного ущерба (см. заметку про IAM ниже).
2. **Триггер Cloud Logging** на эту лог-группу, указывающий на данную функцию.
3. **Сервисный аккаунт** для функции с ролями:
   - `compute.editor` — для чтения и обновления labels инстансов
     (минимально достаточный принцип: ограничьте эту роль конкретным
     каталогом(ами), а не всем облаком)
   - `functions.functionInvoker` — чтобы триггер мог вызывать функцию

## Деплой (Yandex Cloud CLI)

```bash
zip -r function.zip index.py audit_event_parser.py label_sanitizer.py vm_labeler.py requirements.txt

yc serverless function create --name=finops-autotag

yc serverless function version create \
  --function-name=finops-autotag \
  --runtime python312 \
  --entrypoint index.handler \
  --memory 128m \
  --execution-timeout 30s \
  --source-path function.zip \
  --service-account-id <YOUR_SERVICE_ACCOUNT_ID>
```

Затем создайте триггер Cloud Logging на вашу лог-группу, указывающий на
эту версию функции — точные шаги в консоли/CLI см. в
[официальном гайде по триггерам](https://yandex.cloud/ru/docs/functions/concepts/trigger/cloud-logging-trigger).

## Локальный запуск тестов

```bash
pip install -r requirements-dev.txt
pytest tests/ -v
```

`audit_event_parser.py` и `label_sanitizer.py` полностью покрыты без
необходимости в облачных credentials или сетевом доступе. `vm_labeler.py`
намеренно сделан тонким, чтобы его можно было протестировать с
замоканным `InstanceServiceStub`.

## Возможные доработки

- Обобщить `index.py` до диспетчера по `event_type`, чтобы одна функция
  размечала и ВМ, и диски, и managed-базы (маппинг
  `event_type → resource_type → метод API` в конфиге, как описано в
  исходной статье)
- Обогащать `created_by` данными о команде/центре затрат вместо
  сырого IAM-идентификатора
- Пакетная джоба, реализующая исторический/YQL-сценарий целиком
  (расписание → запрос → тегирование), взяв за основу
  `batch_scenario/historical_vm_creators.sql`
- Dead-letter обработка операций тегирования, которые стабильно падают
